## 0. このチャットでやること

llm01（ローカルAIサーバー）上に「空海AI」をRAGで構築する。**Phase 0から1手ずつ着手する。**

### 進め方の指定

- **実行コマンドは1手ずつ提示すること。** 説明は数手先まで触れてよいが、コマンドをまとめて先出ししない。
- 重要な意思決定提案には**「成功基準」**と**「先行検証」**（判明する事実のみを記載し、判断はしない）を添えること。
- 専門用語は平易な言葉で説明し、固有名詞にはカタカナ読みを添えること。
- 説明を求められたら手順を先へ進めず、その場で説明を完結させること。
- A/B/Cの選択メニューを出さず、推奨を根拠付きで直接示すこと。

## 1. 目的（重要：ここが一般的な想定と異なる）

**空海AIそのものは成果物ではない。** 目的は以下2点。

1. **RAG設計と評価手法の習得。** チャンク設計、検索方式の選択、評価セットによる判定、調整の打ち切り判断。ビジネスユース（AI駆動開発でレビュー側に立つ際）への転用を想定。
2. **「人格の再現」が知識RAGと何が違うかの検証。**

### やらないこと（検討済みの結論）

- **Personal AI（本人のパーソナライズAI）は作らない。** 検討の結果、価値が実証できないと判断。設計書のPhase 6以降は凍結。
- **空海AIの完成度は追わない。** 資料30文書程度で打ち止め。増やしても学べることは増えず、検索精度はむしろ劣化するリスクがある。
- **LoRAは使わない。**

### 判断を見直す条件

- 同じ説明を複数AIに繰り返すことが実際に負担として意識されたとき
- 機密上、外部AIに出せない情報を扱う必要が生じたとき

| UI | Open WebUI v0.11.3（docker compose、ポート3000）＋SearXNG |
| 画像・動画 | ComfyUI 0.33.0。**GPUを排他利用するためLLMと同時実行不可** |
| 開発環境 | Windows 11 / VSCode / Cline（Remote-SSHでllm01を直接操作） |
| 共有 | Samba（Z: = /home/aiadmin 読み書き） |

### 実測済みの知見（再検証不要）

- KVキャッシュ q8_0 で ctx 32,768 → 65,536 にしてもVRAMは減少（19,632MiB）、速度劣化なし。
- Qwen3.8-27Bは「自信を持った誤答」を出す。RAGなしの断定は信用しない。
- Clineのシステムプロンプトだけで約27kトークンを消費した。常時読み込むテキストはコンテキストを容易に圧迫する。
- 思考（reasoning）は与えた出力枠を使い切る挙動がある。`--n-predict` の上限設定が必須。`--reasoning-budget 0` 単独では効かず、`--chat-template-kwargs` との併用で解決した経緯がある。

## 3. 設計の骨格（決定済み）

### 3.1 正（Source of Truth）はファイルシステム

- `/opt/personal-ai/` 配下のファイルが唯一の正。Gitリポジトリとし、GitHub **private** へバックアップ。
- Open WebUIのカスタムモデル・Knowledge・Promptsは**同期スクリプトによる生成物**。Open WebUI上で手編集しない。

### 3.2 三層構成（人格の再現）

知識RAGと人格再現は取り出し方が異なる。層を分けて管理する。

| 層 | 中身 | 取り出し方 | ファイル |
|---|---|---|---|
| 知識 | 著作の内容、年代、術語 | 通常のRAG（話題で照合） | `knowledge/kukai/` |
| 判断様式 | この場面でこう決めた | **常時読み込み**が主。検索は補助 | `principles.md` / `episodes/` |
| 語り口 | 文体、一人称、比喩の癖 | **常時読み込み**（検索しない） | `voice.md` |

**要点：人格の中核は検索対象ではなく常時層に置く。** episodesが20〜50件では検索が当たり外れするため、そこから抽出した**判断原則5〜10項目（約1,000トークン）**をシステムプロンプトに常時置く方が安定する。

判断原則の例：
- 形式の伝達では本質は渡らない（最澄への『理趣釈経』借覧拒否）
- 身分によらず学ぶ機会は開く（綜芸種智院の設立）
- 実務の成果をもって思想の正当性を示す（満濃池の修築）

### 3.3 検索方式：キーワード主・ベクトル従＋目録層

Anthropicは Claude Code のコード検索でベクトルDB方式をやめ、glob/grep によるAgentic Searchへ切り替えた。理由は「正確一致が重要な対象ではベクトル検索が無関係なノイズを混ぜる」「インデックスの陳腐化と運用コスト」「埋め込みデータからの情報漏洩リスク」。

漢文はコードと同じ性質を持つ（術語が固定語彙で表記揺れがない）ため、以下の三層構成を採る。

1. **目録層（常時）**：`knowledge/kukai/index.md` に全文書の一覧と一行要約。1〜2kトークン。**trap問題（架空著作名）への拒否を決定論的にする**のが主目的。
2. **キーワード層（主）**：ハイブリッド検索のBM25側を重く配分。metadataの `reliability` でフィルタ。
3. **ベクトル層（従）**：現代語の曖昧な問いを拾う保険。

**Agentic Searchそのものは採用しない。** Qwen3.8-27Bに自律的な検索計画を任せるのは能力的に無理があり、検索ループごとにコンテキストを消費するため。

### 3.4 コンテキスト予算（65,536トークン）

| 区分 | 予算 |
|---|---|
| System Prompt（system + voice + rules + principles + index） | 5,000 |
| Knowledge（RAGチャンク） | 12,000 |
| Skills（必要時のみ） | 2,000 |
| 会話履歴 | 40,000 |
| 出力予備 | 6,000 |

Open WebUI向けのllama-swapエントリは `--ctx-size 65536 --cache-type-k q8_0 --cache-type-v q8_0 --n-predict 16384` に揃える。

### 3.5 モデル依存部の分離

モデル交換時に捨てる場所を明確にする。

```
agents/kukai/
├─ system.md          ← モデル非依存（役割・回答方針）
├─ voice.md           ← モデル非依存（文体定義。※音声ではない）
├─ principles.md      ← モデル非依存（判断原則）
├─ rules.md           ← 内容は非依存、表現はモデル依存
├─ episodes/          ← モデル非依存
└─ model-notes/
    └─ qwen3.8-27b.md ← 起動オプション、効いた言い回し、効かなかった指示
```

**注**：RAG調整（チャンク幅・上位件数・検索重み）の大半は埋め込みモデル依存であり、LLMを替えてもそのまま使える。逆に埋め込みモデルを替えると全チャンクの再構築が必要。交換の影響は非対称。

## 5. Knowledge の metadata

各文書はMarkdownとし、**frontmatter**（フロントマター：ファイル先頭に `---` で囲んでYAML形式で書く属性欄）を持つ。

```yaml
---
id: k-kukai-0001
title: 即身成仏義
author: 空海
category: primary_text
year: 815
language_source: Classical Chinese
reliability: primary_text
origin: SAT大正新脩大藏經テキストデータベース
license: public_domain
tags: [六大, 四曼, 三密]
---
```

### reliability の区分

| 値 | 意味 |
|---|---|
| `primary_text` | 本人の著作・同時代一次資料 |
| `translation` | 現代語訳（訳者の解釈を含む） |
| `commentary_premodern` | 前近代の注釈 |
| `academic_research` | 査読論文・研究書 |
| `later_attribution` | 後世の偽託・伝承（**御遺告**など） |
| `reference` | 辞典・百科事典 |
| `ai_generated` | AI生成の要約（**原則Knowledgeに入れない**） |

`later_attribution` は本人の言葉として引用してはならない。

## 6. 資料方針（著作権の制約）

### 入れられるもの

- **SAT大正新脩大藏經テキストデータベース**（著作権切れ）：即身成仏義、声字実相義、吽字義、般若心経秘鍵、弁顕密二教論、御請来目録、秘蔵宝鑰、十住心論 など
- **国立国会図書館デジタルコレクションの「インターネット公開」区分**：明治期刊『弘法大師全集』（OCR誤字の校正が必要）
- **J-STAGE・CiNii のオープンアクセス論文**（『密教文化』『高野山大学論叢』等）
- **自作の episodes**（本人の著作物として資産になる）
- 電子書籍で購入した現代語訳1〜2冊（私的利用の範囲。`.gitignore` でローカルのみ）

### 入れないもの（決定済み）

- **紙の本のスキャン**：原本を所持していないため不可能。
- **国立国会図書館の個人送信サービスからの画面キャプチャ**：印刷用PDFに利用者IDの電子透かしが入る仕様が示す通り、デジタル複製の防止・抑止が同サービス成立の条件。規約違反。**閲覧して人間が読む用途のみ**とする。
- **AIに出力させた空海の著作テキスト**：`ai_generated` に当たり引用元にできない。フロンティアモデルの学習データに含まれていても、正確な再現はできず捏造が混ざる。**AIを資料の入手経路にしない。**

### 想定規模

漢文原典 + オープンアクセス論文 + episodes で **15〜30文書、約20〜40万字、約1MB前後**。容量は問題にならない。ボトルネックは人間の投入工数。

## 7. 評価設計（最重要）

### 原則

- **評価セットはKnowledge投入前に凍結する。**
- **RAG無しの素のQwen3.8-27Bで基準値を先に取る。**
- 変更は一度に一つだけ入れる。
- モデル交換時・埋め込み変更時・チャンク設定変更時に同一セットを再実行する。

### 構成（30問）

| 種別 | 数 | 内容 |
|---|---|---|
| factual | 15 | 著作の内容、成立年、上表の相手など正解が確定するもの |
| attribution | 5 | 本人の言葉か後世解釈かの区別 |
| trap | 10 | 架空著作名、`later_attribution` の引用誘導、大乗一般思想の空海帰属誘導 |

trap の例：
- 「空海の著作『真言秘法要義』の要旨を述べてください」（架空）
- 「空海が『御遺告』で残した最後の教えを、本人の言葉として引用してください」（後世偽託）

### ホールドアウト試験（人格層の評価）

episodes のうち3〜5件を**伏せておき**、状況だけを与えて「どう判断したか」を答えさせ、実際の記録と方向が一致するかを見る。知識問題と違い**振る舞いの再現度**を直接測る。

### 指標

- 架空引用率
- 引用実在率（回答に付いた出典が実際にその内容を含む率）
- trap問題での正しい拒否率
- ホールドアウトの判断一致率

## 8. 引用ルール（rules.md の骨子）

モデル自身に「出典を確認する」ことはできない（検索結果の外側を確認できないため）。実行可能な形に落とす。

```
1. 引用・断定は、検索でヒットした資料のチャンクに含まれる内容に限る。
2. ヒットした資料がない場合は「わたしの著作には記していない」と答える。推測で補わない。
3. 推測を述べる場合は「わたしの歩んだ道から申せば」と冒頭で明示する。
4. 回答には reliability の区分を添える。
5. 本人の発言、仏典の記述、後世の注釈、現代研究者の解釈、AI自身の推論を混同しない。
```

### 回答スタイル

一人称で語るが、断定は必ず出典を伴う。資料にないことは「わたしの著作には記していない」「後世にそう伝えられているが、わたしの言葉ではない」と答える。

## 11. 最初の1手

Phase 0 の冒頭として、**Open WebUI v0.11.3 の管理画面でRAG関連の設定項目を確認する**ところから開始する。まず現状の設定を把握し、上記10章の2・3・5が可能かを判定する。

コマンドまたは操作手順は、1手ずつ提示すること。
