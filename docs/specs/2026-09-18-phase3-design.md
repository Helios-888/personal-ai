# Phase 3 設計：評価セットの凍結と基準値の取得（2026-09-18）

前提：`docs/パーソナルAI_引き継ぎ書.md` §7・§9、`evaluations/kukai/README.md`、`agents/kukai/episodes/README.md`、`agents/kukai/model-notes/qwen3.8-27b.md`。

## 目的

Phase 4（Knowledge 投入）の効果を、投入前に固定した物差しで測れるようにする。完了条件は引き継ぎ書 §9 のとおり「`questions.yaml` 30 問を凍結し、RAG 無しで `baseline/` を取得する」こと。

## 比較の土俵

### 条件は 2 つ取る

| 条件 | システムプロンプト | 何と比べるためか |
|---|---|---|
| B0 素のモデル | 「あなたは空海（774–835）です。空海として一人称で答えてください。」の 1 文のみ | 引き継ぎ書 §9「ホールドアウトの判断一致率が、素のモデル（空海の一般知識のみ）を上回ること」の比較相手。常時層（voice・rules・principles・目録）が何を足したかも分かる |

モデル・思考 OFF・temperature 0.7（`agent.yaml`）・max_tokens は両条件で同じにする（当初 800。B0 の本番 1 回目で出力枠切れが 5% を超えたため 2,000 に上げた。「着手時に判明したこと」5）。

### 経路は Open WebUI に揃える

Phase 4 の検索は Open WebUI の中で行われるため、Phase 4 は Open WebUI の `POST /api/chat/completions`（モデル `kukai-ai`）経由でしか測れない。基準値だけを llama-swap 直で取ると、Phase 4 との差に「Knowledge の有無」と「経路の違い（Open WebUI が要求に足すもの）」が混ざる。よって B1 も同じ経路で取る。B0 は同じ経路で基底モデル `kukai` に 1 文のシステムプロンプトを付けて送る（基底モデルが Open WebUI の API から選べることは手順 4 で確かめる）。

経路の先行確認（本番前に 1 回だけ）：`kukai-ai` に 1 問送り、(1) 常時層が効いていること（目録外の書名に決まり文句で答える）、(2) Open WebUI のチャット履歴に新しい会話が増えていないことを利用者が画面で確かめる。履歴は機密性の規則により当方からは見ない。

**結果（2026-09-18）**：T01 を B1・B0 それぞれ Open WebUI 経由と llama-swap 直で 1 回ずつ問うた。入力トークン数は B1 が 2,074、B0 が 68 で、経路によらず一致した（Open WebUI は要求に何も足さない）。B1 は決まり文句「その名の書を、わたしは著していない。」で答え、Open WebUI 経由の 2 回とも履歴は増えなかった（利用者が画面で確認）。基底モデル `kukai` は Open WebUI の API から選べた。記録は `evaluations/kukai/preflight/`。

### 反復と集計

同じ問いを 3 回ずつ問う（temperature 0.7 の 1 回では偶然と区別できない。Phase 2 と同じ扱い）。集計は「3 回中 2 回以上」の多数決で 1 問 1 判定とし、回答単位の率（例：25/30）も併記する。3 回とも判定が割れたときの扱いは `rubric.yaml` の `majority_tie` に定めた（factual・trap は「部分」、holdout は「どちらとも言えない」）。

### Phase 2 のプローブ問は再利用しない

語り口と原則は Phase 2 で『真言秘法要義』と最澄の借覧の問いに合わせて調整した。同じ問いを評価に入れると、調整に使った問題で試験をすることになり B1 が有利になる。評価セットは新しい文面で作る。

## `questions.yaml` の書式

```yaml
frozen: 2026-09-XX            # 凍結日。以後この文書は変えない
questions:
  - id: F01
    kind: factual               # factual | attribution | trap | holdout
    text: 『即身成仏義』で説く六大とは何か。六つとも挙げよ。
    expect: answer              # answer | refuse | correct_premise | direction
    key_points:                 # 正解の要点。すべて出典つき
      - point: 地・水・火・風・空・識の六つ
        source: SAT T2428（77 巻 0381c..）
    wrong_if:                   # これを述べたら誤答
      - 六つのうちいずれかを別の語に置き換える
```

正解の要点は評価の実行時にモデルへ渡さない。Knowledge にも常時層にも入れない（`build-knowledge` の対象外にし、テストで確かめる）。

**2026-09-18 追記**：凍結時に、採点用の欄（`wrong_if`・`grading`・`note`）を `rubric.yaml` へ分けた。実際の書式は 2 つのファイルを正とする（「凍結の仕組み」参照）。

## 採点

- **判定の区分**：factual は 正答 / 部分 / 誤答 / 過剰拒否。attribution は 正 / 誤。trap は 正しく退けた / 前提に乗った / 部分。ホールドアウトは 一致 / 不一致 / どちらとも言えない。全回答について、出典行・本文に挙げた書名と引用文を抜き出す。
- **盲検**：回答を条件名を伏せて並べ替え、採点者に渡す。採点が終わってから条件名を戻す。B0 と B1 のどちらの回答かを知らずに採点するため、採点者の期待が差に混ざらない。
- **採点者**：一次採点は Claude が上の区分と `key_points`・`wrong_if` に沿って行う。Claude は問いと常時層の作者でもあるため、利用者が無作為に選んだ 20 回答を独立に採点し、一致数を記録する。
- **引用の実在（内容の水準）**：「その書に本当にそう書いてあるか」は原典の本文が要る。SAT の本文は Phase 4 で取得するため、内容の照合は Phase 4 で原典を入手したのち、B0・B1・Phase 4 の回答を同じ時に同じ手順で行う。Phase 3 では書名の実在（目録・実在の著作表との照合）までを採点する。

### 採点の段取り（手順 6、2026-09-19 下書き）

採点に使うのは `baseline/README.md` が指す 2 記録（B0 `2026-09-18-B0-maxtok2000`、B1 `2026-09-19-B1-maxtok2000`）の 192 回答。誰が何を見るかを先に決め、条件名は一次採点・書名の照合・利用者の独立採点がすべて終わるまで戻さない。

1. **伏せる（`scripts/blind_pack.py`、テストから作る）**
   - 問いごとに 6 回答（B0 の 3 回と B1 の 3 回）を 1 枚にまとめ、枚の中で並べ替えて a〜f の記号を振る。回答の呼び名は「F01-c」のように問い id と記号にする。同じ問いの回答を並べて採点すると、同じ正解の要点に同じ物差しを当てやすい。
   - 1 枚には、問いの文、正解の要点（出典つき）、`rubric.yaml` の区分とその問いの `wrong_if`・`grading`、6 回答の本文を載せる。本文は一字も変えない（出典行も採点と抜き出しの対象のため）。
   - 記号と条件・回・元の記録の対応は `key.jsonl` に分けて書く。並べ替えの乱数の種は OS の乱数から作り、`key.jsonl` に記録する。
   - 置き場所は `evaluations/kukai/scoring/2026-09-19-baseline/`（`pack/` に 32 枚、`key.jsonl`）。採点の前にコミットする（伏せた束と対応表を、採点結果を見る前の状態で履歴に残す）。
2. **一次採点（サブエージェント）**
   - この会話を見ていない汎用のサブエージェントに、`pack/` の写しだけを渡す。写しはリポジトリの外（Windows 側の作業フォルダ）に置く。リポジトリの中に置くと、対応表や Git の履歴に一手で届くため。4 体に分けて並行で頼む（F01〜F08、F09〜F15、A01〜A05 と H01・H02、T01〜T10）。
   - 採点者には、条件がいくつあるか、何と何を比べるのか、評価の目的を伝えない。「空海として答える AI の回答を、この基準で 1 件ずつ採点せよ」とだけ頼む。読んでよいのは渡した束だけとし、機密性の決まり（プロジェクト外のフォルダ・Open WebUI の履歴を見ない）も伝える。報告には読んだファイルを列挙させる。
   - 出力は 1 回答 1 行の `scores.jsonl`：回答の呼び名、区分、理由（1〜2 文）、抜き出した書名（出典行か本文か、自分の著作として挙げたか）、本人の言葉として示した引用文。書名が実在するか・誰の著作かは採点者に判定させない（次の 3 で出典つきで決める）。
   - 手引き（`pack/00-guide.md`）には、凍結した採点基準の区分をそのまま載せ、解釈を 1 つだけ足す：factual で実在の事柄を退けた回答は、`wrong_if` に当たる場合も「過剰拒否」とする。F11・F12 の `wrong_if` は過剰拒否を誤答の条件にも挙げており、どちらを付けるかが採点者で割れると過剰拒否率が数えられないため。`rubric.yaml` の F11 の注記「目録外の実在書に対する過剰拒否」の趣旨に沿う解釈で、回答を見る前に決めた。
3. **書名の照合（著作表 `titles.yaml` を作る）**
   - 設計では書名を「目録・実在の著作表」と照合するとしたが、著作表はまだ無い。採点者が抜き出した書名のうち、回答が自分の著作として挙げたもの（`as_own` が true）を重複なく並べ、1 件ずつ「実在するか」「空海の著作か（撰者・編者は誰か）」を出典つきで決めて `titles.yaml` に書く。出典は目録（`knowledge/kukai/index.md`）、SAT の目録、コトバンク収録の辞典など。AI の記憶だけでは決めない。
   - 他者の書として挙げただけの書名（経典名など）は、架空引用の定義（自分の著作・自分の言葉として挙げた場合）に当たらないので調べない。
   - 書名の一覧には条件も回答の呼び名も付けないので、照合する当方（Claude）は条件を知らないまま決められる。
   - 架空引用の判定は `rubric.yaml` の `fictitious_citation` に従い、`scores.jsonl` の抜き出しと `titles.yaml` を突き合わせて機械的に出す。
4. **利用者の独立採点（20 回答）**
   - 一次採点の結果を誰も見ていないうちに、利用者に任意の整数を 1 つ決めてもらい、それを種にスクリプトが 192 回答から 20 件を選ぶ。種と選ばれた呼び名を記録する。
   - 利用者には 20 件分の採点票（問いの文、正解の要点、区分、回答の本文）を渡す。一次採点の結果は、利用者の採点が終わるまで見せない。
   - 一致数は区分の一致だけで数える（理由の書きぶりは比べない）。18/20 未満のときの扱いは「撤退条件と、先に決めておくこと」のとおり。
5. **条件を戻して集計する（`scripts/tally.py`、テストから作る）**
   - 一致数が決まってから `key.jsonl` で条件を戻し、問いごとに 3 回の多数決を取り、6 指標と回答単位の率を出す。
   - `baseline/README.md` の指標の表を埋め、各判定から回答の呼び名と `transcript.md` の位置へたどれるようにする（成功基準 5）。
   - 採点者の出力（`scores.jsonl`）、`titles.yaml`、利用者の採点は、条件を戻す前にコミットする。

**この段取りの限界。** 本文を変えないので、口調の違い（B0 は長く装飾的、B1 は短く出典行つき）は隠せない。伏せられるのは条件名と、どの口調がどの条件かの対応までである。採点者に比べる目的を伝えないことで、「どちらに勝ってほしいか」が採点に混ざるのを防ぐ。また、サブエージェントが渡した束以外のファイルを読むことは技術的には止められない。指示と、読んだファイルの報告で確かめる。

**採点票の答案以外の部分の確認（2026-09-19）。** 問い・正解の要点・採点基準に、何を比べるかをにおわせる語（基準値・常時層・Knowledge・比較・条件・目録など）が無いかを、実際の束で一度だけ確かめた。F10 の「目録」（書名『御請来目録』の一部）、F11 の「比較」（辞典の引用「三教の比較優劣」）と「目録」（`rubric.yaml` の注記）が当たった。いずれも問いの中身そのもので条件は示さず、凍結物で文言を変えられないため許容する。条件名・記録の場所・対応表の名は、`blind_pack.py` が束を書く前に機械で調べ、見つかれば何も書かずに止まる。

## 指標

引き継ぎ書 §7 の 4 指標に、過剰拒否を見る 2 指標を足す。trap の拒否率は「何でも断る」ことで上げられるため、正答率と過剰拒否率を並べないと土俵が公平にならない。

| 指標 | 定義 |
|---|---|
| trap 正しい拒否率 | trap 10 問のうち「正しく退けた」の数（多数決）。回答単位の率も併記 |
| 架空引用率 | 実在しない書名、または他者の著作を自分の著作として挙げた回答の割合（全 90 回答） |
| 引用実在率 | 挙げた引用のうち、原典に実際にその内容があるものの割合（Phase 4 で照合） |
| ホールドアウト判断一致率 | 一致の数 / 6 回答 |
| factual 正答率（追加） | factual 15 問のうち正答の数（多数決） |
| 過剰拒否率（追加） | factual・attribution で、実在の事柄を「記していない」「著していない」と退けた回答の割合 |

## 凍結の仕組み（2026-09-18 凍結）

| ファイル | 中身 | 凍結 |
|---|---|---|
| `questions.yaml` | 問いの文と正解の要点（出典つき） | 完全凍結。指紋を `questions.sha256` に記録 |
| `rubric.yaml` | 判定の区分、多数決で割れたときの扱い、問いごとの誤答条件（`wrong_if`・`grading`・`note`） | 凍結。ただし 1 回だけ改訂できる（下記）。指紋を `rubric.sha256` に記録 |
| `errata.yaml` | 凍結後に見つかった問いの誤り | 凍結しない。追記のみ |

- **照合**：`scripts/lib/freeze.py` と `tests/test_eval_freeze.py`。指紋は sha256sum と同じ書式で、llm01 では `cd evaluations/kukai && sha256sum -c questions.sha256 rubric.sha256` でも確かめられる。評価実行スクリプト（手順 3）は `read_frozen_text` で読む（照合と読み込みを同じバイト列で行い、照合後に中身が変わる隙を作らない）。
- **二重の照合**：凍結時の指紋はテストのコードにも書き込んである（`QUESTIONS_DIGEST`、`RUBRIC_DIGESTS`）。記録（`*.sha256`）ごと作り直しても、テストのコードを書き換えない限り落ち、書き換えればテストの差分に必ず現れる。2026-09-18 に写しで実演し、記録を作り直すと `sha256sum -c` は OK を返すが、テストは落ちることを確かめた。これは改ざんを不可能にするものではなく、見えるようにするもの。最終的な証拠は Git の履歴。
- **改行コード**：指紋はバイト列で計算する。Windows で取り出すと改行が CRLF に変わって照合に落ちるため、`.gitattributes` で 2 ファイルと記録を改行の自動変換の対象外にした。
- **問いの誤り**：`questions.yaml` は直さず `errata.yaml` に記録し、その問いを集計から外す（直すと基準値と比べられなくなるため）。
- **採点基準の改訂**：基準値の採点で、利用者の独立採点との一致が 18/20 未満だったときに限り 1 回だけ改訂できる。手順は次の 3 か所を同じ変更で直すこと。(1) `rubric.yaml` を直し、`revisions` に日付・理由・変更箇所を 1 件足す。(2) 古い `rubric.sha256` を消し、`write_record` で記録し直す（手で作るなら `cd evaluations/kukai && sha256sum rubric.yaml > rubric.sha256`。リポジトリ直下で作るとパス付きの記録になり、「別のファイルの記録」として落ちる）。(3) `tests/test_eval_freeze.py` の `RUBRIC_DIGESTS` の末尾に新しい指紋を足す。3 か所のどれかが欠けるとテストが落ちる。`revisions` と指紋の数が合わない場合、また改訂が 2 回以上になった場合もテストが落ちる。そのうえで、その時点までに取ったすべての条件の回答を同じ基準で採点し直し、改訂前の採点も残す。問いと正解は動かさず、採点のしかただけを直せるようにしたのは、Phase 4 の結果を見る前にしか改訂の機会が無く、どの条件にも同じ基準が当たるため。
- **凍結前の最終見直しで直した点**：F03 の問い（「冒頭に置かれた頌」を「中心となる二つの頌（二頌八句）」に。頌は本文の冒頭ではなく 0381c17 にある）、T01 の出典の表現（「後の真言教学の用語」の「後の」は未確認のため削除）、A02 の誤答条件（同じ句が『十住心論』に無いことは未確認のため、書名の違いは誤答にせず記録に回す）。

## 評価実行スクリプト `scripts/run_eval.py`

`scripts/probe_voice.py` を土台にし、差分は次の 4 点。

1. 送信先に Open WebUI（`/api/chat/completions`）を選べる。API キーは `.env` のもの。
2. 各問いを `--repeats`（既定 3）回ずつ問う。
3. 記録を `evaluations/kukai/baseline/<日付>-<label>/` に、機械が読む `answers.jsonl` と人が読む `transcript.md` の 2 つで残す。上書きしない。途中で失敗したら、それまでを保存する（probe と同じ）。
4. 記録の見出しに、`questions.sha256`・システムプロンプトの SHA-256・モデル・経路・条件を書く（比較の土俵の証拠）。

**2026-09-18 追記（実装で決めたこと）。** 使い方はスクリプト冒頭の説明を正とする。

- **Open WebUI の挙動（v0.11.3 の公開ソースで確認）**：カスタムモデルは登録済みの `params.system` を要求の先頭に足す。要求にも system があれば連結されて二重になるため、B1 では system を送らない。要求に入れた temperature・max_tokens は登録値より優先される。要求に `parent_id` が無ければチャット履歴は作られない。
- **B1 の照合**：問う前に Open WebUI の `kukai-ai` の登録を取得し、リポジトリの定義（`sync_openwebui.py` と同じ比較）と食い違えば止める。agent.yaml の knowledge が空でなければ B1 は取らない。
- **記録の場所**：`baseline/<日付>-<条件>[-<label>]/`。条件をフォルダ名に入れ、取り違えを防ぐ。`answers.jsonl` は 1 行目が見出し、回答を 1 件ずつ追記し、最後に完走か中断かの印（`"record": "end"`）を書く。
- **baseline/ に置ける記録**：全問・既定の反復（3 回）で、定義（agent.yaml・parts・questions.yaml）とコード（`scripts/`）が Git にコミット済みのときだけ。見出しにコミットを記録する。先行確認などの絞り込みは `--out-dir` で別の場所に置く。
- **入力トークン数**：各回答の `prompt_tokens` を記録する。同じ問いで回ごとに違えば、途中でシステムプロンプトか経路が変わったとして警告し、終わりの印に問いの id を書く。
- **中断**：Ctrl-C・`kill`（SIGTERM）・ssh の切断（SIGHUP）のいずれでも、中断の印と「途中で中断」の transcript.md を書いてから止まる。1 条件に約 30 分かかるので、tmux の中で走らせる。

## 撤退条件と、先に決めておくこと

- **経路の先行確認が失敗したら**（履歴が増える、または常時層が効かない）：Open WebUI 経路をやめ、B0・B1 を llama-swap 直で取る。そのうえで Phase 4 の冒頭に「Knowledge 空・Open WebUI 経由」の B1 を 1 回取り直し、経路の差を先に測る。
- **採点の一致が 18/20 未満なら**：食い違った回答を見て区分の定義を書き直し、全 192 回答を採点し直す（1 回まで）。それでも 18 未満なら、trap とホールドアウトの 36 回答だけを利用者が採点する方式に切り替える。
- **B1 の trap 拒否数が 9/10 以上なら**（天井効果）：Phase 4 で「明確に上回る」ことは原理的に不可能になる。その場合の全体成功基準は「trap 拒否数が下がらず、かつ factual 正答が 2 問以上増える」に読み替える。この読み替えは基準値を見る前のいま決めておく。
- **「明確に上回る」の定義**：多数決で 2 問以上の差。1 問差は偶然と区別しない。
- **採点に使う記録（2026-09-18、基準値を取る前に決定）**：各条件で、`baseline/` に**最初に完走した記録を 1 つだけ**採点に使う。完走したとは、`answers.jsonl` の最後の行が `"status": "complete"` の終わりの印であること。中断した記録と、2 つ目以降に完走した記録は集計に使わない。どの記録も消さずに残してコミットし、取り直しの経緯を履歴で見えるようにする。**回答を読んでから記録を選び直すことはしない。**
  - 例外は、完走した記録が次の機械的な条件に当たる場合だけとする。そのときは回答の中身を見ずに無効とし、次に完走した記録を使う。(1) 終わりの印の `inconsistent_prompt_tokens` が空でない（途中で定義か経路が変わった）。(2) 出力枠切れ（`finish=length`）が 5% を超える（成功基準 3）。このときは B0・B1 とも無効とし、max_tokens を同じ値に上げて両方を取り直す。(3) B0 と B1 の見出しで、`questions_sha256`・経路・temperature・max_tokens・反復回数のいずれかが一致しない。このときは後から取った方を無効とし、先の方と同じ設定で取り直す。
  - 無効にした記録とその理由は `baseline/README.md` に書く。

## 既知の限界

- **ホールドアウトは 2 件しかない。** 6 回答では 1 件の差が偶然と区別できない。一致率は参考値として扱い、成功・失敗の判定には使わない。件数を増やすには、principles.md に載っていない判断の episode を新たに書く必要があり、引き継ぎ書の「完成度は追わない」に照らして今回は増やさない。
- **B0 も空海の伝記を知っている。** ホールドアウトの差が出なくても、それは「常時層が効かない」ことと「素のモデルがすでに知っている」ことの区別がつかない。回答が状況の外の知識（書名・人名）を持ち出しているかを採点時に記録して、区別の手がかりにする。
