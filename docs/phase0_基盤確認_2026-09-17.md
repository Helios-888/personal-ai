## 2. 未確認事項（引き継ぎ書 §10）の確認結果

### 10-1. Filter Function（フィルター・ファンクション）の仕様 — 確認済

会話の前後に Python を挟む仕組み。v0.11.3 のフックは 4 つ。

| フック | 呼ばれる時点 | 用途の例 |
|---|---|---|
| `inlet(body, __user__, __event_emitter__, __model__, __metadata__, __request__)` | ユーザー発話ごとに 1 回、**検索の前** | 質問の整形、ログ |
| `request(body, __user__, __features__)` | **検索の後**、LLM 呼び出し直前 | 検索で挿入されたチャンク（`<source id=.. name=..>` タグ）を見て加工・検査できる |
| `stream(event, __metadata__)` | 出力の逐次チャンクごと | 語尾の置換など |
| `outlet(body, __user__, __metadata__)` | 回答完成後 | 引用の検証・記録（評価指標「引用実在率」の自動計測に使える） |

- モデル単位の有効化：管理画面 → Models → 該当モデル編集 → Filters。API では `ModelForm.meta.filterIds`。
- 全体有効化：Functions 画面の地球儀アイコン（global）。
- `file_handler = True`（モジュール直下）を書くと**組み込み RAG を止めて自前検索に置き換え**られる（§3 の選択肢 C）。
- 現在 Function は 0 件。

出典：https://docs.openwebui.com/features/extensibility/plugin/functions/filter/ 、`backend/open_webui/routers/functions.py`（v0.11.3）

### 10-2. ハイブリッド検索と BM25 重み — 設定は存在、ただし §3 の問題あり

- 設定項目（管理画面 Documents / API `POST /api/v1/retrieval/config/update`）：`ENABLE_RAG_HYBRID_SEARCH`（現在 false）、`HYBRID_BM25_WEIGHT`（0〜1、現在 0.5。0 以下でベクトルのみ、1 以上で BM25 のみ）、`TOP_K`、`TOP_K_RERANKER`、`RELEVANCE_THRESHOLD`、`ENABLE_RAG_HYBRID_SEARCH_ENRICHED_TEXTS`。
- 合成方式：LangChain の EnsembleRetriever（RRF：順位の逆数を重み付きで足す方式）。
- **重み比率は設定できる**。ただし BM25 側が漢文・日本語で 0 点しか返さないため、現状では重みをいくら振っても効かない（§3）。

出典：`backend/open_webui/config.py`、`retrieval/utils.py`、`routers/retrieval.py`（いずれも v0.11.3）

### 10-3. リランカーを CPU で動かせるか — 確認済（CPU でしか動かない）

- 読み込みは `sentence_transformers.CrossEncoder(model, device=DEVICE_TYPE)`。コンテナは CPU 版 torch のため DEVICE_TYPE は cpu。GPU を llama-swap / ComfyUI と取り合うことはない。
- 外部リランカー（`RAG_RERANKING_ENGINE=external`、任意の HTTP サーバー）も選べる。
- 候補：`BAAI/bge-reranker-v2-m3`（多言語・568M）、`hotchpotch/japanese-reranker-cross-encoder-small-v1`（日本語・小型）。
- **未計測**：CPU での 1 質問あたりの遅延。Phase 5 の比較条件に含める（目安：top_k 20 件の並べ直しで数秒以内なら実用）。

### 10-4. REST API で カスタムモデル・Knowledge・Prompts を作成・更新 — 確認済

### 10-5. チャンク設定と frontmatter フィルタ — 設定場所は確認済、frontmatter フィルタは **不可**

- 設定：管理画面 Documents。`TEXT_SPLITTER`（`character` / `token` / `token_transformers`）、`CHUNK_SIZE`、`CHUNK_OVERLAP`、`CHUNK_MIN_SIZE_TARGET`（小さすぎるチャンクを前後と結合）、`ENABLE_MARKDOWN_HEADER_TEXT_SPLITTER`（見出しで先に分割、見出しはチャンクの metadata `Header 1..` に入る）。
- `.md` は LangChain `TextLoader` でそのまま読む。**frontmatter は剥がされずに本文として最初のチャンクに残る**。
- チャンク metadata：`file_id, name, source, hash, created_by, start_index, embedding_config` ＋ Markdown 見出し。アップロード時の `metadata` JSON も file.meta に保存される。
- **しかし会話時の検索関数に metadata フィルタの引数がない**（ハッシュ重複検知でだけ内部的に filter を使っている）。→ 引き継ぎ書の代替案どおり**フォルダ分け＝ reliability 区分ごとに Knowledge を分ける**。
- 追加の工夫：LLM に渡るタグは `<source id="1" name="ファイル名">` なので、**ファイル名に区分を含める**（例 `later-attribution__御遺告_T2431.md`）と、全チャンクで区分が LLM に見える。frontmatter は最初のチャンクにしか残らないため、この方が確実。

### 10-6. 日本語・漢文混在に強い埋め込みモデル候補 — 候補は絞れた、選定は要実測

コンテナは CPU 実行。sentence-transformers 名をそのまま `RAG_EMBEDDING_MODEL` に設定できる。

| 候補 | 規模 | 根拠 | 懸念 |
|---|---|---|---|
| `BAAI/bge-m3` | 568M | 100 言語対応（中国語・日本語とも）。仏教漢文の検索で評価実績（MITRA 論文、ファインチューン前でも動作） | JMTEB（日本語ベンチ）では ruri に劣る |
| `cl-nagoya/ruri-v3-310m` | 310M | JMTEB Retrieval 81.89 で日本語最上位クラス。zenn の 2000 問実測でも bge-m3 と同等以上 | 日本語特化のため漢文（古典中国語）の語彙被覆が未知 |
| `intfloat/multilingual-e5-large` | 560M | 多言語の定番 | JMTEB Retrieval 70.98 で上 2 者に劣る |

**推奨**：まず `bge-m3`。理由は、資料が漢文＋現代日本語の混在で、質問は現代日本語という「言語をまたぐ検索」になるため、多言語モデルの方が設計意図に合うこと。
- 成功基準（最安の先行検証、30 分・CPU）：空海著作 8 点の冒頭 200 字ずつと、それぞれに対応する現代日本語の質問 8 問を用意し、質問→正しい著作の top-1 命中率を bge-m3 と ruri-v3-310m で比較。命中率が同等なら bge-m3、ruri が明確に上回れば ruri。
- 注意：埋め込みモデル変更は全チャンク再投入が必要（30 文書なら数分）。ただし Phase 4 投入前に決めるのが安い。

出典：https://secon.dev/entry/2025/06/11/100000-qwen3-embedding-jmteb/ 、https://zenn.dev/fp16/articles/aa48dcae23974e 、https://arxiv.org/pdf/2601.06400（MITRA）

## 3. 重要な発見：BM25 が漢文・日本語で機能しない（設計 3.3 への影響）

### 先行検証（判明した事実のみ）

1. v0.11.3 の `retrieval/utils.py` は `BM25Retriever.from_texts(texts, metadatas)` を**分かち書き関数なし**で呼ぶ（コンテナ内の実コード 544 行目で確認）。
2. LangChain（0.4.2）の既定の分かち書きは `text.split()`＝空白区切り（コンテナ内で関数ソースを確認）。
3. コンテナ内で実験：空海著作 3 本の漢文チャンクと現代日本語 1 本に対し、4 種の質問を投げた BM25 スコア。

| 質問 | 既定（空白区切り） | 文字 2-gram に置換した場合 |
|---|---|---|
| 六大 | 全文書 0.00 | 即身成仏義 0.70、他 0.00 |
| 六大とは何か | 全文書 0.00 | 即身成仏義 0.70、他 0.00 |
| 即身成仏 六大 四曼 三密 | 全文書 0.00 | 即身成仏義 2.11、他 0.00 |
| 恵果 灌頂 | 全文書 0.00 | 伝記（現代日本語）1.74、他 0.00 |

4. BM25 側の分かち書きを変える設定項目は v0.11.3 に存在しない（`RAG_TOKENIZER_MODEL` はチャンク分割用）。
5. `ENABLE_RAG_HYBRID_SEARCH_ENRICHED_TEXTS` を ON にすると、BM25 用テキストに**ファイル名**（`_ - .` を空白に置換）と見出しが追加される。ファイル名を分かち書き済みの形にすれば、書名の完全一致だけは BM25 で拾える余地がある（未検証）。
6. 論文など現代日本語の資料も同じく空白がないため、BM25 は現状コーパス全体で無効。

### 推奨（根拠つき）

**Phase 4 の初回投入は「ベクトル＋リランカー＋目録層」で行い、BM25 は使わない。** 理由は、この構成なら Open WebUI の設定だけで成立し、変数を増やさずに基準値との差を取れるため。trap 問題（架空著作名）の拒否は設計どおり目録層（index.md を常時読み込み）に担わせ、術語の正確一致はリランカー（cross-encoder は文字列を直接見るため漢文でも機能する）に頼る。

**Phase 5 の比較条件の一つとして「文字 2-gram BM25 ハイブリッド」を入れる。** 実現手段の候補は、Filter Function のモジュール直下で `open_webui.retrieval.utils.BM25Retriever` を 2-gram 分かち書き付きのサブクラスに差し替える方法（Function は Open WebUI と同一プロセスで動くため理屈上は可能。v0.11.3 に固定されている前提で成立。**未検証**、10 分の動作確認が先行検証になる）。これで「漢文検索にキーワード一致は効くのか」という学習目的の問いに、同じ 30 問で数値の答えが出せる。

- 成功基準：30 問中の「引用実在率」と「trap 正答率」が、ベクトルのみの条件を上回ること。
- 撤退条件：差し替えが動かない、または 2 条件で指標差が 1 問分以内なら BM25 を捨て、Open WebUI 標準構成に戻す。

## 4. コンテキスト予算の実測（kukai エントリ、2026-09-17）

| 項目 | 実測 |
|---|---|
| モデル | Qwen3.8-27B-Q4_K_M（公式、ファイル 19.0 GB）。mmproj（画像用）なし |
| 起動オプション | `--ctx-size 65536 --n-predict 16384 --n-gpu-layers 99 --cache-type-k q8_0 --cache-type-v q8_0` |
| 初回ロード＋短文応答 | 17 秒 |
| スロット | 4 スロット、各 n_ctx 65536（現行 llama-server ではスロットごとの値。`/slots` で確認） |
| 長文入力 | 40,071 トークンを切り詰めなしで受理。プロンプト処理 1,018 tok/s、所要 42 秒 |
| 生成速度 | 36.5 tok/s（入力 62 トークン時）、28.9 tok/s（入力 40k トークン時） |
| VRAM | 20,906〜20,908 MiB / 24,576 MiB。長文入力後も増えない（KV は起動時に確保） |
| 引き継ぎ書の値との差 | 19,632 MiB は Uncensored 版（ファイルが 1.0 GB 小さい）での測定値。差はモデルサイズで説明できる |
| 思考（reasoning） | 既定で ON。max_tokens 64 の質問では思考だけで出力枠を使い切り本文が空になった（引き継ぎ書の知見を再現） |
